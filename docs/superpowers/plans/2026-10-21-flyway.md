# Flyway e privilégio mínimo (lote 9) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Versionar o schema com Flyway, rodado num passo separado com `chefhome_migracao`, e fazer a API usar só `chefhome_app` (DML) com `ddl-auto: validate`.

**Architecture:** A `V1__schema_inicial.sql` é gerada pelo Hibernate a partir das entidades (dialeto PostgreSQL) e revisada à mão. Um script de setup cria o schema `chefhome` e as duas roles. Um teste com Testcontainers aplica setup e migrations num Postgres real e sobe o contexto como `chefhome_app` com `validate`.

**Tech Stack:** Java 17, Spring Boot 4.0.5, Hibernate 7, Flyway 11.14.1 (versão do Boot), Testcontainers 2.0.4 (`testcontainers-postgresql`, `testcontainers-junit-jupiter`), PostgreSQL 17.

**Spec:** `docs/superpowers/specs/2026-10-21-flyway-privilegio-minimo-design.md`

## Global Constraints

- Schema `chefhome`, com as roles `chefhome_migracao` (dona do schema) e `chefhome_app` (só DML). As senhas entram por `psql -v` e nunca são versionadas.
- A `V1` reproduz **exatamente** o mapeamento atual, inclusive:
  - os nomes `usuarios`, `chefe`, `endereco` (FK `user_id`), `agendamentos` (FKs `user_id` e `endereco_id`), `agendamento_chefe`, `pratos` (FK `chefe_id`), `notificacao` e `denuncia`;
  - as sequences `endereco_seq`, `agendamentos_seq` e `pratos_seq` (`INCREMENT BY 50`, por causa do `GenerationType.AUTO`);
  - o `status` de agendamento como ordinal;
  - os defaults `chefe.suspenso false`, `disponivel true` e `ativo true`.

  Qualquer diferença em relação às entidades faz o `validate` falhar, e esse é o teste.
- Índices extras na `V1`: `denuncia(chefe_id, status)`, `denuncia(cliente_id, chefe_id, status)`, `endereco(user_id)`, `agendamentos(user_id)` e `pratos(chefe_id)`, além do índice de `notificacao` que já existe.
- A API não ganha Flyway no runtime: `flyway-core` e `flyway-database-postgresql` entram só em `test` e no plugin. O perfil `test` (H2) continua com `create-drop`, sem mudança.
- `MigracoesPostgresIT` usa `@Testcontainers(disabledWithoutDocker = true)` e roda no `mvn test` padrão.
- **Para verificar localmente,** o Docker Desktop precisa estar ligado. Sem ele o IT é *pulado*, e pulado **não conta** como verificado. Nesse caso, pedir ao usuário que ligue o Docker antes de considerar a Task 2 concluída.
- Testes: `./mvnw -q clean test -Dspring.profiles.active=test`. Para contar, some `tests=` e `skipped=` dos `TEST-*.xml`.
- **Não commitar** `src/main/resources/application-prod.yml` nem `application.example.yml` (as alterações locais do usuário). Na Task 3, o `application.example.yml` é **reescrito por inteiro**: perguntar ao usuário antes de sobrescrever o conteúdo local dele. Commit sempre por caminho, e os commits terminam com `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **`chefhome_app` tentando `CREATE TABLE`** em `chefhome` **e** em `public` → permissão negada. Teste na Task 2.
2. **Tabela criada por uma migration futura** (V2): o `chefhome_app` já consegue ler e gravar sem um `GRANT` manual, por causa dos default privileges. Teste na Task 2, criando uma tabela de teste como `chefhome_migracao` depois das migrations.
3. **Inserir endereço, agendamento e prato** como `chefhome_app` funciona, o que exige `USAGE` nas sequences. Teste na Task 2.
4. **Rodar o script de setup duas vezes** não dá erro (idempotente). Teste na Task 2.
5. **Entidade e `V1` divergindo:** o contexto não sobe. Teste na Task 2, pois o próprio `validate` é a asserção.

### Task 2: Roles de privilégio mínimo e teste de migração no Postgres

**Files:**
- Create: `db/setup/01_usuarios.sql`, `src/test/java/com/couto/chefe_api/MigracoesPostgresIT.java`
- Modify: `pom.xml` (dependências de teste `org.testcontainers:testcontainers-postgresql`, `org.testcontainers:testcontainers-junit-jupiter`, `org.flywaydb:flyway-core` e `org.flywaydb:flyway-database-postgresql`, todas em `test` e sem versão, gerenciadas pelo Boot)

**Interfaces:**
- O script lê as variáveis `:senha_migracao`, `:senha_app` e `:"nome_banco"`, e é idempotente (`DO $$ BEGIN IF NOT EXISTS (SELECT FROM pg_roles ...) THEN CREATE ROLE ...`).
- `MigracoesPostgresIT`:
  - `@SpringBootTest`, `@ActiveProfiles("test")`, `@Testcontainers(disabledWithoutDocker = true)`;
  - `@Container static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:17-alpine")`;
  - um `static` inicializado antes do contexto (num `@DynamicPropertySource`) roda o setup (via `psql` dentro do container, com `execInContainer`) e depois o `Flyway.migrate()` como `chefhome_migracao`;
  - as propriedades dinâmicas são `spring.datasource.url` (com `?currentSchema=chefhome`), `username=chefhome_app`, `driver-class-name=org.postgresql.Driver`, `spring.jpa.hibernate.ddl-auto=validate` e `spring.jpa.database-platform=org.hibernate.dialect.PostgreSQLDialect`.

- [ ] **Step 1: Escrever os testes:**
  - `contextoSobeComValidateComoApp`, um método vazio: subir o contexto já prova o item 5 do Review Focus;
  - `appGravaELeEmTodasAsTabelasComSequence`: via JDBC como `chefhome_app`, inserir usuário, endereço, chef, agendamento e prato (pelo `EntityManager` ou pelos repositórios) e ler de volta;
  - `appNaoCriaNemApagaTabela`: `CREATE TABLE chefhome.x(id int)`, `CREATE TABLE public.x(id int)` e `DROP TABLE chefhome.usuarios` → todos lançam `SQLException` com SQLState `42501`;
  - `defaultPrivilegesCobremTabelasFuturas`: como `chefhome_migracao`, `CREATE TABLE chefhome.futura(id int)`; depois, como `chefhome_app`, `INSERT` e `SELECT` nela funcionam;
